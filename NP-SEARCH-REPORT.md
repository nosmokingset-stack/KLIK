# KLIK — оптимизация Новой почты, 27.11.2026

## Подтверждённые причины

В исходной `directory.js` задержка города составляла 450 мс перед каждым запросом. Кэша браузера и объединения одинаковых запросов не было. При выборе города `loadPoints` последовательно запрашивал все страницы по 200 строк и лишь затем создавал все option в datalist. Для Харькова фактически получено 1771 доступное отделение/почтомат за 10 HTTP-запросов; повторный поиск снова делал те же 10 запросов. Общий серверный lock, защитный интервал API и обратные задержки при лимитах могут дополнительно растягивать некэшированный поиск. Их нельзя безопасно просто убрать ради скорости.

Изучены HTML/CSS/JS NOSMOKINGSET и непосредственно его Apps Script сервера заказов. `getWarehouses_` делает один запрос с SettlementRef, Page=1, FindByString и лимитом 20 (не более 50). Серверного CacheService в этом исходнике нет; клиентского кэша справочника и полной предварительной выгрузки города в изученном клиенте тоже нет. Задержки ввода в нём — 430 мс для города и 360 мс для точки. Значит, преимущество отделений обусловлено объёмом и числом запросов, а не более коротким debounce или скрытым кэшем. Поиск передаётся POST text/plain; KLIK сохраняет собственный JSONP для публичного справочника и отдельный POST для заказа.

NOSMOKINGSET использовался только для чтения и безопасных запросов справочника. Его код, свойства, таблицы, развёртывания и сайт не изменены. Исходники и идентификаторы приватного сервера не публикуются в KLIK.

## Что изменено

- `directory-search.js`: кэш только публичных ответов на 180 секунд, максимум 70 записей; память и localStorage, без данных покупателя. Нормализация запросов, дедупликация одинаковых активных обращений, очереди с приоритетом последнего ввода. Новое изменение строки сразу делает старый ответ неактуальным, в том числе при очистке/короткой строке.
- Debounce: 150 мс для городов, 100 мс для нового сетевого поиска точек. Совпадения из кэша показываются без debounce. Открытие точки после выбора города начинает её предварительную загрузку.
- Новый серверный `pointsSearch`: один ограниченный запрос FindByString, прежняя проверка города и фильтрация работающих отделений/почтоматов, русские альтернативные названия и адреса. Существующие ограничения API и проверка точки при заказе сохранены.
- До redeploy автоматически работает старый сервер: первая страница доступна сразу, следующие загружаются в фоне. Поиск по уже полученным данным локальный; при выборе точки фоновая выгрузка прекращается после текущего запроса. Для далёкой ещё не полученной точки на старом сервере по-прежнему может понадобиться несколько страниц — это не выдаётся за устранённую серверную задержку.
- Списки являются абсолютными оверлеями под полем, той же ширины, не сдвигают форму. Есть ограниченная прокрутка, выделение, стрелки/Enter/Escape/Tab, закрытие после выбора и вне поля. Сохранены синие/жёлтые цвета и шрифты KLIK; другие секции не переоформлялись.
- При переключении языка повторный config-запрос не нужен. Непосредственно перед заказом свежая серверная конфигурация, цена и доступность по-прежнему перепроверяются.
- На таймауте JSONP оставляется временный безопасный callback, чтобы поздний ответ не вызывал ошибку. При раннем исчезновении регистрации города из CacheService предусмотрена одна ограниченная попытка обновления; бесконечных повторов нет.

## Реальные замеры в Chrome, мс

В каждой паре использованы реальный публичный справочник KLIK, запрос «Харків», один и тот же компьютер и отдельные браузерные контексты. «Первый» означает холодный **кэш браузера**, «повтор» — повтор в том же контексте. Общий серверный кэш не очищался и его состояние для этих HTTP-замеров неизвестно. Это отдельные измерения, не медианы серии и не гарантированный SLA.

| Сценарий | 1440 px до | 1440 px после | 390 px до | 390 px после |
| --- | ---: | ---: | ---: | ---: |
| Первый поиск города | 2282 | 2466 | 1988 | 2101 |
| Повторный поиск города | 1899 | 8 | 2989 | 7 |
| Первые доступные точки | 13396 | 1137 | 13945 | 1716 |
| Повторный поиск точек | 12865 | 39 | 15114 | 39 |

Первый поиск города заметно не ускорился: задержка Google Apps Script и сети остаётся. Уменьшение debounce не перекрыло разброс сети. Повторный поиск города и точек не отправлял новых запросов справочника. Старый клиент перед показом ждал все 1771 записи; новый показывает до 30 подходящих вариантов из первой страницы. Остальные записи не потеряны: они подгружаются либо запрашиваются адресно после включения нового сервера.

В первом новом сценарии до выбора точки начались два запроса страниц: первая уже показана, вторая подгружается. После выбора следующая страница не запрашивается. В старом сценарии до появления выбора начинались и завершались все 10. Время включает браузерный ввод/выбор и ожидание отрисовки; 39 мс повторного выбора не означает 39 мс сетевого API.

## Развёртывание

Directory.gs уже сохранён в отдельном исходном проекте **KLIK Orders**. Для включения pointsSearch в публичном web-app нужно обновить существующее развёртывание KLIK на новую версию, сохранив URL и доступ. Текущий опубликованный web-app пока не менялся. Клиент совместим с ним и уже даёт измеренное улучшение через первую страницу и кэш.

Не меняйте API-ключ, SPREADSHEET_ID, таблицу, флаг приёма заказов или скрипты NOSMOKINGSET. Обновлённый XML в Blogger не устанавливался. После согласованного redeploy нужно повторить HTTP-замеры точечного режима через браузер: ниже приводятся отдельные серверные измерения из редактора, они не заменяют время web-app round trip.

Ограничение CacheService: запись может исчезнуть до TTL. Это учтено, а не считается гарантированным хранением: [официальная справка Google](https://developers.google.com/apps-script/reference/cache/cache-service).
